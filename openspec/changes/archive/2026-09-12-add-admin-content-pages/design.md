## Context

See proposal.md for why. What shapes the approach:

- Medusa v2.13 supports custom modules with their own tables and migrations, custom admin and store routes with zod body validation in `src/api/middlewares.ts`, and admin UI routes under `src/admin/routes/` whose exported config puts them in the sidebar. Nested route directories with their own config appear as children of the parent sidebar item. The Resend provider under `api/src/modules/resend/` is already a custom module, so the extension points are in use.
- Store routes require the publishable key by default; admin routes require an authenticated admin by default. Nothing extra is needed for either.
- The admin bundle is built by Vite from `api/src/admin/`. `@medusajs/ui`, `@medusajs/icons` and `@medusajs/js-sdk` are not direct dependencies of `api/` today, so admin screens cannot import them until they are added.
- The storefront already renders markdown with `react-markdown` inside the `prose` typography for product descriptions. `react-markdown` does not render raw HTML by default.
- The storefront data layer: reads are `server-only`, wrapped in `cached` with a key, tags and a 60-second revalidate, and return `{ data, error }` without throwing. The shop page's metadata sets `noindex` and drops the canonical when the data layer reports an error.
- The footer already lists `/privacy`, `/shipping-returns` and `/terms`. `PUBLIC_PATHS` in `front/lib/routes.ts` feeds the sitemap and the e2e SEO test mirrors it.
- The seed script runs in CI on a fresh database and once by hand on a new environment. Migrations run on every deploy through `pnpm predeploy` in the API entrypoint.
- The owner is a Lithuanian sole trader (individuali veikla), not a VAT payer, shipping to Lithuania and the EU with one Lithuanian option and one Rest of Europe option. Sizes and rates come from the admin, and the current shipping page's numbers match the seed.

## Goals / Non-Goals

**Goals:**

- A fresh environment renders complete, correct policy pages with no manual step. The admin edits override, never bootstrap.
- Admin screens that look native, with no state library and no editor dependency.
- Every write on the API goes through a workflow, every read on the storefront through the cached data layer, exactly like the catalog.

**Non-Goals:**

- Generic CMS features: arbitrary pages, blocks, media library, drafts, history.
- Instant propagation of edits. The catalog already tolerates a minute; so do the policies.
- Lithuanian translations.

## Decisions

**1. Two modules, one per domain.** `api/src/modules/content-page/` holds `content_page` (`id`, `slug` unique, `title`, `description`, `body`, timestamps) with its service and slug list. `api/src/modules/gallery/` holds `gallery_item` (`id`, `url`, `title`, `rank`, timestamps), its service. Each module is registered unconditionally in `medusa-config.ts` because it is application data, not an optional external service, and the migrations are generated with `medusa db:generate content gallery` and run with the existing predeploy step. Two modules because the docs scope a module to one domain and these share nothing: `content` is the owner-edited pages, as on the storefront, and `gallery` is the video list. Alternative: product or collection metadata as a store for page text. Rejected because there is no natural product to hang a privacy policy on and the admin's key/value editor is a poor place for a page of markdown. The gallery stores the embed URL, not the pasted link or a video id: `api/src/api/admin/gallery/validators.ts` turns any YouTube link shape into `https://www.youtube.com/embed/<id>`, the admin validator rejects everything else, and the storefront frames the stored URL as is, so the provider rules live in one place on the API.

**2. Page text is owner data, never source.** The owner writes every screen in the admin: a page without a row answers 404 from both routes, the storefront renders its 404, and the admin card shows an empty state whose Edit creates the row. `api/src/scripts/seed/content-pages.ts` fills the missing rows with lorem ipsum from `@faker-js/faker`, a devDependency, so development and CI have pages to render; it never runs on production. `seed.ts` calls it. This follows the Medusa standard for initial data, a script under `src/scripts/` run with `medusa exec`; the docs keep loaders for setup and discourage seeding from them. Alternatives: markdown files in the repository as production defaults, rejected because content is not code, legal text drafted by a developer is a liability and the owner should never need a deploy to change a word; a loader inserting rows at boot, rejected for the startup side effect in both containers.

**3. The slug set is a constant.** `CONTENT_PAGE_SLUGS = ['privacy', 'terms', 'shipping-returns', 'about'] as const` in the module's `types.ts` is the only list. Each route file names its slug and resolves the content page service itself, as the Medusa docs do; the service's `retrieveBySlug` throws `MedusaError` `NOT_FOUND`, so no route helper layer exists. The shared zod schema lives in `api/utils/validators.ts`, the one place the core keeps shared validators. The admin screens are one static route per slug, and the storefront keeps its own route-to-slug map in `front/lib/routes.ts` because the projects cannot share code. The API list and the storefront list are pinned by the integration test and the e2e test.

**4. Writes are workflows.** `saveContentWorkflow({ slug, title, description, body })` and `saveGalleryWorkflow({ videos })`, each one step with a compensation that restores the previous rows. The routes only validate and invoke. This follows the API rule that side effects never run inline in a route, and matches how the contact route delegates to a workflow. The gallery save replaces the whole list: it deletes the stored rows and inserts the posted ones with `rank = index`. One request and one workflow for every gallery action: the screen posts the whole list after a create, an edit, a remove or a drop. Alternative: separate add, remove and reorder endpoints, rejected because a reorder then needed a permutation check to stay consistent and three routes did the work of one.

**5. YouTube link validation on the API.** The `url` field is validated by a zod schema in `api/src/api/admin/gallery/validators.ts`, next to the route like every core validator. It accepts the three link shapes a YouTube video gives you, `youtube.com/watch?v=`, `youtu.be/` and `youtube.com/embed/`, rejects anything else naming `url`, and transforms the accepted link into the embed URL once. The admin drawer only requires a non-empty link and shows the API's message under the field, so the schema is the single gate. The stored value is the embed URL, so the storefront never parses.

**6. Validation in `middlewares.ts`.** `validateAndTransformBody` with zod schemas from `@medusajs/framework/zod` for `POST /admin/(privacy|terms|shipping-returns|about)` and `POST /admin/gallery`, in the same `middlewares.ts` the contact change introduces, so the two changes add entries to one file rather than each creating it. Limits: title 1 to 120, description 0 to 300, body 1 to 100000, video title 1 to 120, at most 100 videos.

**7. Admin screens: one component per shape, plain SDK calls.** Each screen is a top-level sidebar item: `api/src/admin/routes/<slug>/page.tsx` for each slug renders `<ContentPageCard slug="…" />` from `api/src/admin/components/content-page-card.tsx` with a label, an icon and a `rank` that orders the five items. The card copies the dashboard's record pages such as Store settings: a header with the title and a `DropdownMenu` with Edit, then one label and value row per field, or an empty state when the page has no row yet. The body renders through `react-markdown` with compact admin text components in `components/markdown.tsx`, so a heading in the body is a bold small line and nothing competes with the card header. Edit opens `components/content-page-drawer.tsx`, a `Drawer` with the three fields and Cancel and Save. `react-markdown` is ESM only, so the admin is typechecked with its own bundler-mode `src/admin/tsconfig.json` and excluded from the root CommonJS run; `routes/gallery/page.tsx` renders `<GalleryEditor />`. There is no Content group: Medusa only nests routes under a parent that has its own page, and a page whose only job is to hold the group is one screen too many. Both use `@medusajs/ui` (`Container`, `Heading`, `Input`, `Textarea`, `Button`, `Table`, `toast`). The gallery screen copies the dashboard's Categories page: a `Container` with a header band holding the `Heading`, a subtitle and two small secondary buttons, Edit ranking and Create, then a full-width `Table` whose rows end in a `DropdownMenu` with Edit and Delete. Create and Edit share one `Drawer` with the URL and title fields; Delete goes through `usePrompt`. Edit ranking opens a `FocusModal` whose body is the flat drag list the categories organize screen uses, one row per video with a `DotsSix` handle, and every drop saves. The drag uses `@dnd-kit/core`, `@dnd-kit/sortable` and `@dnd-kit/utilities`, the library the dashboard already uses there, added at the dashboard's versions. The dashboard's own `DataTable`, `ActionMenu` and `RouteFocusModal` wrappers are internal to its bundle, so the screen uses the public `@medusajs/ui` pieces with the same classes and an `sdk` instance from `@medusajs/js-sdk` configured with `auth: { type: 'session' }` in `api/src/admin/lib/sdk.ts`, the pattern the Medusa docs use. Data loads in `useEffect` into component state; there are five screens with one request each, so `@tanstack/react-query` is not added. `@medusajs/ui@4.1.1`, `@medusajs/icons@2.13.1` and `@medusajs/js-sdk@2.13.1` are added to `api/` devDependencies at the versions the bundled dashboard already uses, so the bundle keeps one copy of each. Alternative: a dynamic `pages/[slug]` route and a table, rejected because dynamic routes cannot appear in the sidebar.

**8. Storefront data layer.** `front/lib/data/content-page.ts` is `server-only` and exports `getContentPage(slug)` returning `{ contentPage, error, notFound }`; `front/lib/data/gallery.ts` exports `getGalleryVideos()` returning `{ videos, error }`. Both go through `sdk.client.fetch` against the store routes, wrapped in `cached` with keys `['content-page', slug]` and `['gallery']`, tags `content-page-<slug>` and `gallery`, and the 60-second revalidate. A 404 becomes `notFound: true`; any other failure logs and returns the error with `content: null` or `videos: []`. React `cache()` wraps them so `generateMetadata` and the page body share one fetch per request, as the product page does.

**9. One view, four routes.** `front/components/content-page/content-page-view.tsx` takes a slug, calls `getContentPage`, and renders the `Heading` in blackletter plus `<ReactMarkdown>` inside `prose max-w-none`, calls `notFound()` when there is no row, or shows the error alert. A `contentPageMetadata(contentPage, path)` helper in `front/lib/seo.ts` builds title, description and canonical, or `robots: { index: false }` without a canonical when the read failed, mirroring the shop page. The four route files under `front/app/(main)/` each export `generateMetadata` and render the view with their slug and path; the old hard-coded shipping and about pages are deleted. `/gallery` reads `getGalleryVideos` and keeps its current player markup, plus the empty and error states. Heading levels inside the body start at `##` in the seed files so the page keeps one `h1`.

**10. Routes and footer.** `front/lib/routes.ts` gains `CONTENT_PAGES`, a list of `{ slug, path }` for the four pages, and `PUBLIC_PATHS` derives from it instead of listing `/shipping-returns` by hand. The footer builds its links from the three policy entries plus their labels. The e2e SEO test's path list gains `/privacy` and `/terms`.

**11. Checkout consent line.** The paragraph under the Place order button in `payment-step.tsx` becomes "By placing your order you accept the Terms & Conditions and the Privacy Policy. Your card is charged only when the order is placed." with the two names as links opening in a new tab. Placement under the button, not a checkbox: EU consumer law requires the customer to be informed before ordering, not to tick a box, and a checkbox is one more way to abandon the checkout.

**12. Seeded content.** Each seeded page has the fixed title the storefront and admin use, a lorem ipsum description and three lorem ipsum sections whose headings start at `##`, so the page keeps one `h1`. The owner writes the real policies in the admin. The seller identity block is the same in the three policies: name, "individualios veiklos pažymos Nr." followed by the number, address, email `contact@h2bcweb.com`.

**13. Seed and tests.** `seed.ts` runs the parts in `src/scripts/seed/` in order: `store.ts`, `products.ts`, `content-pages.ts`, `gallery.ts`. Each is a `medusa exec` script of its own. Development and CI run all four; production runs none of them for content. `api/tests/content.test.ts` uses `medusaIntegrationTestRunner` and holds only tests: `api/tests/support/auth.ts` creates a publishable key and an admin user with a signed JWT before each test, `support/data.ts` holds the page and video fixtures, `support/gallery.ts` the URL helpers and `support/http.ts` the error response helper. `tests/content.test.ts` opens the four pages and the gallery against the seeded API and checks the heading, a body element, the gallery players, the footer link from the cart, and the consent line on the payment step reached the way `checkout.test.ts` reaches it. `tests/admin.test.ts` drives the admin as the store owner and checks the admin screens only: the new video is the last row, the saved body shows on the card. What reaches shoppers is the API suite's job, so the root tests never call the API and hold no publishable key; only the storefront does, from its env. No test skips: an empty shop or a missing key fails with a message. The admin journey runs in its own Playwright project after the storefront project, since it adds a video and rewrites a page while the storefront journeys assert the seeded state. The owner login `admin@h2bc.local` is created by `src/scripts/seed/admin-user.ts`, so a reseed or a fresh CI database has it.

**14. Documentation.** `docs/architecture.md` stays one line per folder under extension points, with the two modules, the seed parts, the workflows and the admin routes added to their lines; the fact that page text and the gallery are owner data goes under Admin-owned data; the data layer, caching and SEO sections gain the new reads, tags and pages.

## Risks / Trade-offs

- [Owner never writes the pages] → The migration plan makes it the first post-deploy step, the checkout consent line links to pages that answer 404 until then, and the production storefront is not indexable until `SEO_INDEXABLE` is set.
- [Markdown pasted from Word brings odd characters] → `react-markdown` renders text safely and never HTML; nothing can break the page layout beyond ugly formatting the owner sees on the site within a minute.
- [Admin bundle grows with `@medusajs/ui`] → The dashboard already ships it; pinning the same version keeps one copy.
- [A save from a stale screen overwrites a concurrent change] → One owner edits the gallery, and a save replaces the whole list with what that screen shows.
- [Two slug lists, API and storefront] → Each side's test pins its list; a mismatch fails CI on the 404 page.

## Migration Plan

1. Merge. The predeploy step creates the two tables. The four pages answer 404 and the gallery is empty on production until the owner fills them in.
2. In the live admin, add the three videos, then write the privacy, terms, shipping and about pages, each policy with the seller identity block.
3. Read the three policies once on the live site before `SEO_INDEXABLE` is switched on.

Rollback is a revert plus dropping the two tables; no other data is touched.
